FH MCP Bridge · Lesson 2 of the course

Orienting Claude, then asking a question you can trust the answer to

Lesson 1 covered when it's safe to ask. This one covers how to ask well — so the answer you get back is actually grounded in your tree, not a plausible-sounding guess, and so you have a habit for catching it when it isn't.

There's no command list — and that's the point

Every question you ask becomes a fresh, purpose-written script against FH's own API. There is nothing to memorise — ask however you'd ask a research colleague: "who died between 1914 and 1918 in France or Belgium", "how many Munros are in the tree", "who are so-and-so's grandparents". If a question is genuinely ambiguous — an unclear place-name spelling, an unspecified number of generations — Claude will ask you to clarify rather than guess.

Why this matters for you specifically

Because the script is written fresh each time against your project's own schema, it reads your project's own custom Fact types by their real, resolved tags — not as a raw GEDCOM FACT/EVEN plus a TYPE subtag the way they'd sit in an export. A military-history project's own _ATTR-REGIMENT or EVEN-ENLISTED facts are first-class here. No fixed command set could have anticipated your project's specific customisations — this is what makes "who died while serving in the armed forces" answerable at all, for a project set up that way.

Orient first: start with the census

Before asking a substantive question of a project Claude hasn't seen yet, ask for an overview — "give me an overview of this project". That runs a fixed, built-in census (record counts per type, plus how often each tag and custom fact appears) — cheap, always Read-only regardless of your Session's Access mode, and it gives Claude the same lay of the land you already have in your head. Skipping it doesn't break anything, but a fresh Session with no orientation is more likely to mis-guess an ambiguous tag name on a project it hasn't touched before.

The verification habit

An answer that "looks wrong" is more often a scripting slip than a data problem — Claude runs a fresh script per question, so an unusual question can occasionally expose a bug in that script rather than tell you something true about your tree. The fix is always available and costs nothing extra:

"Can you double-check that?" / "Explain how you got that number."

Claude has full context on the exact script it just ran and can walk through its logic — or re-run it a different way — on request. Treat an unverified surprising answer the way you'd treat a suspiciously convenient GEDCOM import: plausible, not yet trusted.

A separate, no-Session tool: FH's own help

Claude can also search Family Historian 8's bundled official help — menus, features, dialogs, plugin authoring — without any Bridge Session running, since it doesn't touch your tree at all. Useful for "how do I get FH to do X" questions that have nothing to do with your live data.

Quick check

Claude gives you a count that looks too low. What's the right first move?

Try it now

  1. Start a Read-only Session and ask for a project overview first.
  2. Ask one real research question, phrased naturally, using a custom Fact type you know is specific to this project.
  3. Pick one answer and ask Claude to explain how it got it — even if it looks right — just to build the habit before you need it for one that looks wrong.
