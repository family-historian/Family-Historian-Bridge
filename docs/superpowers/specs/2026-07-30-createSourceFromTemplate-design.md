# `createSourceFromTemplate` — a permanent helper for creating templated Source records

## Context

Creating a Source record from a Source Template (e.g. "Civil Registration Certificate")
via `run_lua` currently requires hand-assembling several undocumented steps every time:
find the `_SRCT` template record, walk its `FDEF` field definitions to learn their exact
`CODE`/`TYPE`, link the new `SOUR` record to the template (`_SRCT` child tag), create each
field as a metafield using a `~PREFIX-CODE` shortcut string (prefix depends on the field's
declared type), set each value with the setter matching its *value kind* rather than its
field-type name, enable auto-titling, and separately create a `TEXT` child for a
transcription. This was done by hand once (creating source #41, Nellie Record's 1895 birth
certificate) and is now documented as domain knowledge in
`server/data/gedcom-knowledge-corpus.jsonl` (`source-template-creating-a-templated-source`).
Documentation alone still leaves Claude re-deriving the same multi-step script from scratch
every time, with the same chances to get a step wrong. This spec covers building it once as
a reusable capability instead.

## Goals

- Eliminate re-deriving the `_SRCT`-link + metafield-shortcut dance by hand on every call.
- Validate field data (unknown field codes, invalid Enum values) before any mutation, so a
  bad call never leaves a partially-created record behind.
- Fit the project's existing architecture and testing conventions rather than introducing a
  new kind of surface.

## Non-goals

- Attaching the created Source as a citation to a Fact/Individual/Family record. Source
  creation and citation attachment are separate concerns; this spec covers creation only.
- A new MCP tool. See "Rejected approaches" below.
- Any change to `describe_project`, `run_lua`, or `author_fh_plugin`'s own tool schemas.

## Approach

Add `bridge/sourceHelper.lua`, a plain Lua module in the same shape as `sandbox.lua` /
`runScript.lua` / `requestFraming.lua` (no FH/socket dependency of its own, `require`'d
rather than reimplemented). It exposes one function:

```lua
local sourceHelper = require('sourceHelper')
sourceHelper.createSourceFromTemplate(templateNameOrId, fields, transcription)
```

This is exactly the same idiom as `fhUtils`' own helpers (`addFamilyAsChild`, `createFact`,
etc.) that `run_lua`'s hardened tool description now points Claude toward — this fills the
one gap `fhUtils` itself doesn't cover (there is no `fhUtils` function for creating a
templated Source record from scratch). No new MCP tool, no new wire protocol, no change to
the `LUA`/`LUA_RO` request framing.

### Sandbox wiring — the one correctness-critical decision

`sourceHelper.lua` calls the *real* global `fhCreateItem`/`fhSetValueAsLink`/etc. directly
(the same way `fhUtils` itself does), not the sandboxed copies in a script's `_ENV`. If
`sandbox.lua` exposed `env.fhBridge` unconditionally, a **read-only** Session could call it
and it would still actually mutate the tree — silently bypassing the read-write gate issue
#14 built. `sandbox.lua` must therefore wire:

```lua
if accessMode == "read-write" then
  ...
  env.fhBridge = require('sourceHelper')
end
```

inside the *existing* `if accessMode == "read-write"` block, exactly alongside
`fhCreateItem`/`fhSetValueAsLink`. Under read-only, `env.fhBridge` is nil, same as every
other write capability — no new gating mechanism, just one more line in the block that
already exists.

### Function signature and semantics

```lua
-- sourceHelper.createSourceFromTemplate(templateNameOrId, fields, transcription)
--
-- templateNameOrId: string (matched case-insensitively against the target _SRCT record's
--   own NAME field — must match exactly one template, or this errors listing what it
--   found) or integer (a _SRCT record id, e.g. from a prior lookup).
--
-- fields: table mapping a field CODE (exactly as declared in the template's own FDEF,
--   e.g. "Type", "Principal_2") to a value:
--     - Text / Name / Place / Address / Enum -> plain Lua string
--     - Date -> either a Date object already built via fhNewDate(y, m, d[, subtype]), or
--       a plain table { year = , month = , day = [, subtype = ] } which the helper
--       converts via fhNewDate for you
--     - Repository -> an item pointer to an existing REPO record
--     - URL -> plain string
--   Every key in `fields` must match a real FDEF code on the resolved template. Every
--   value for an Enum-typed field must be one of that field's own declared options
--   (parsed from its FDEF's PROM, pipe-separated, e.g. "Birth | Marriage | Death |
--   Divorce").
--
-- transcription: optional string. If given, becomes the record's "Text from Source" (TEXT
--   child tag), stored as plain text (fhNewRichText(transcription, false) — not parsed as
--   FTF markup).
--
-- Returns: { id = <new SOUR record id>, title = <auto-generated title after refresh> }
```

Field-type dispatch to the correct setter is based on the field's declared `TYPE` from its
`FDEF` (Text/Name/Place/Enum -> `fhSetValueAsText`; Date -> `fhSetValueAsDate`; Repository
-> `fhSetValueAsLink`; URL -> `fhSetValueAsText`), not on any type information the caller
supplies — the caller only supplies plain Lua values (see `fields` above) and the template
itself is the source of truth for how each one gets set.

### Execution order — validate everything, then mutate

1. Resolve `templateNameOrId` to exactly one `_SRCT` record. Error if zero or more than one
   match.
2. Walk the template's `FDEF` children, building a map of `CODE -> {TYPE, allowed enum
   options}`.
3. For every key in the caller's `fields` table: error if no matching `FDEF` code exists;
   for Enum-typed fields, error if the value isn't one of the parsed options.
4. Only once every field passes validation: create the `SOUR` record, create its `_SRCT`
   link to the template, create and set each metafield (dispatched per step 2's type map),
   create the `TEXT` transcription if given, then `fhSrcEnableAutoTitle(sour, true)`.

Because validation is a fully separate pass before any `fhCreateItem("SOUR")` call, a bad
call never leaves a half-created orphan record — there is nothing to roll back on the
common failure path (unknown field, bad Enum value, ambiguous template name).

### Error handling

No new mechanism. Any failure (unresolved template, unknown field code, bad Enum value, or
a genuine FH-side runtime failure during creation) is a Lua `error(...)`. `runScript.lua`'s
existing `pcall` wrapper turns that into the same JSON `{"error": "..."}` shape every other
`run_lua` failure already produces. FH's own auto-undo (ADR 0005) remains the backstop for
a genuinely unexpected failure *during* creation (step 4) — the validation pass (steps 1-3)
is what keeps that backstop rarely needed rather than load-bearing.

## Testing

`sandbox.test.lua` / `runScript.test.lua` / `requestFraming.test.lua` all stub flat,
no-op functions because none of them need a working fake *tree*. This helper genuinely
walks `MoveToFirstRecord` / `MoveToFirstChildItem` / `MoveNext` / `IsNotNull` to find a
template and its `FDEF`s, then calls `fhCreateItem` / `fhSetValueAsLink` / etc. to build a
new one — so testing the full resolve-validate-create path needs a small in-memory fake
item-pointer double, not just stubbed functions. This is genuinely new test infrastructure
for this repo (the first "fake tree" rather than the first "fake flat function"), scoped
narrowly to only the item-pointer methods this helper actually calls:
`MoveToFirstRecord`/`MoveToFirstChildItem`/`MoveNext`/`IsNotNull`/`IsNull`/`GetTag`, plus
fakes for `fhGetItemText`/`fhGetRecordId`/`fhCreateItem`/`fhSetValueAsText`/
`fhSetValueAsDate`/`fhSetValueAsLink`/`fhSetValueAsRichText`/`fhNewDate`/`fhNewRichText`/
`fhSrcEnableAutoTitle`. Lives alongside the module as `bridge/sourceHelper.test.lua`, run
the same way as the other `*.test.lua` files (`lua bridge/sourceHelper.test.lua`, no FH
dependency).

Coverage should include: creating a Source with every field type represented (Text, Name,
Date via both a Date object and the table shorthand, Place, Address, Repository, Enum,
URL), an unknown field code erroring before any mutation, an invalid Enum value erroring
before any mutation, template resolution by both name and id, an ambiguous/missing name
erroring clearly, the transcription field being set as plain (non-FTF) text, and
`fhSrcEnableAutoTitle` being called with the record's own pointer after all fields land.

A manual end-to-end step should be added to `bridge/README.md`'s existing manual-test
list, in the same style as steps 11-12 added for issues #14/#16: start a read-write
Session, call `fhBridge.createSourceFromTemplate(...)` against a real template in a real
project, and confirm the resulting Source record's fields and auto-generated title in FH's
own UI. Also confirm the read-only negative case: the same call under a read-only Session
fails calling `fhBridge` as nil, the same way any other write attempt does.

## Rejected approaches

- **A new dedicated MCP tool** (`create_source_from_template`, mirroring `describe_project`'s
  pattern of a fixed script behind a typed tool schema): would need a Lua-code-generation
  step on the server side with careful value-escaping to embed the caller's field data into
  a generated script — a new complexity/risk surface this project doesn't currently have
  anywhere. It would also duplicate the sandbox's own read-write gating in a second place
  (the server-side tool would need its own check, separate from `sandbox.lua`'s). Rejected
  in favor of reusing the existing `run_lua` transport and the sandbox's existing gating
  mechanism as-is.
- **Documentation only** (the `gedcom-knowledge-corpus.jsonl` entry and hardened `run_lua`
  description already committed): doesn't eliminate re-deriving the multi-step dance by
  hand each time, which was the actual problem being solved here.
