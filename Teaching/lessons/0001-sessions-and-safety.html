Sessions, Access mode, and why you can't permanently break anything

You already know Family Historian cold. What's new here is one extra layer sitting on top of it: the Bridge. This lesson gives you the one thing you need before you ask Claude a single question — how a Bridge Session works, and exactly what stops a mistake (yours or Claude's) from becoming permanent.

The Session: FH is locked while Claude can reach it

In FH, open the AI Assistant Connector plugin dialog and click Start. That begins a Session — the window in which Claude can send it queries. Three things to know about a Session:

  • FH's main window locks for the whole Session. This is deliberate, not a bug — it stops you and Claude editing the same project at once. You get it back the moment the Session ends.
  • A Session ends when you click Stop, after 5 minutes idle, or when you close the dialog entirely (Exit).
  • Access mode is chosen once, at Start, and holds for the whole Session. To change it, Stop and Start again.

Why this is safe

In Read-only mode, the write functions aren't a locked door Claude could pick — they're not in the room. The script it writes literally has no way to call fhCreateItem, fhDeleteItem, or any fhSetValueAs* setter. There's no "oops, it wrote anyway" failure mode to worry about here.

Read-write, and why a bad edit still isn't permanent

Read-write is where your "without damaging my database" worry actually lives, so here's the real mechanism — not just reassurance:

FH's own undo, not the Bridge's

The Bridge implements no undo logic of its own. It doesn't need to — every change it makes goes through FH's own native undo system, the same one that backs every edit you make by hand. That means:

  • Ctrl-Z always reverts the last change, exactly as if you'd made it yourself in the FH UI.
  • If a write script errors partway through, FH automatically undoes it — a half-applied change doesn't get left sitting in your tree.
What Ctrl-Z doesn't cover

Undo protects you within a session of work, same as it always has in FH — it's not a substitute for your own backup discipline. If you don't notice a bad edit until three Sessions later, Ctrl-Z won't reach back that far. Treat a Read-write Bridge Session exactly like any other editing session in FH: back up first if you'd be upset to lose the file, same as you already would before a big manual edit.

Try it now

  1. Open your FH project and start a Session — pick Read-only first.
  2. Ask Claude a research question you already know the answer to (a good way to calibrate trust in its output before you lean on it for the unknown).
  3. When you're ready to try Read-write, back up the project file first, then ask Claude to make one small, low-stakes edit and watch it happen live in FH.
